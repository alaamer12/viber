The narration

  1. Enter. The user types /viber init in a repo that has nothing Viber in it. run
  2. Who am I serving? First run asks <USERNAME> and stores it in the registry header. ask
  3. Scan the deck. Every registered Skill is read — metadata only, the top of each SKILL.md — global folders, the project, plus any extension repos the user names. Nothing is copied; the registry is an index. step
  4. Classify. Each Skill becomes Viber or Deck, gets a scope, an area (design · code · research…), its viber: tag, and any name conflicts are recorded, not resolved silently. step
  5. Ask exclusions, state consequences. "Which deck Skills stay out of the umbrella?" — every exclusion ships with its price written next to it; the tag declares, the deck decides. ask
  6. Files come to exist. state
    • .viber/registry.md — this project's snapshot of the deck.
    • .viber/memory.md · settled.md · learnt.md — the ledger, empty templates, capture-on-arrival from now on.
    • AGENTS.md gains (or gets) its ## Viber section — the declaration that turns supervision on for every later session.
    • .viber/.data/viber.json — the per-project census, seeded from the master and filled while studying the deck: serves, doing, why per skill.
  7. Layout duties. .gitignore carries artifacts/ and scratch/; the .viber share-or-ignore question is asked once and the answer recorded. ask
  8. Never assume completion. Existing docs or code are surveyed and marked Needs Review — a file existing is not proof its skill ran. step
  9. Start. Fresh repo → Phase 1, first mandatory step: idea-md. From here the Router drives: every session reads the declaration, reroutes relocatable knowledge under .viber/, and answers POSSIBLE NEXT STEPS with last: → why → do: from the census. run
